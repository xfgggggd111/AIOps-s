# AIOps 智能运维实战精品班第 2 期干货：容量预测、故障演练实操技巧

业务持续增长、流量波动、营销活动带来的突发峰值，是运维长期面临的压力，容量规划过去依靠人工经验估算，经常出现资源浪费或者突发扩容不及时。本期课程聚焦容量预测与故障演练两大落地模块，面向中大型业务集群，讲解可直接复用的实操思路，帮助团队把容量管理标准化、故障验证常态化。

容量预测和普通指标预测有明显区别，它关注的不是短期波动，而是中长期资源水位、饱和拐点，核心目标是预判资源耗尽时间，指导扩容、缩容、资源调度。做容量预测第一步，先梳理资源与业务的关联关系，建立业务流量到 CPU、内存、连接数、磁盘 IO、带宽的映射基线，也就是资源转化率。很多团队容量评估失真，就是直接拿原始指标做预测，忽略业务结构变化：接口改版、用户结构变化、缓存命中率变化，都会改变单位流量的资源消耗。

特征构建上，除了历史流量、周期特征，必须纳入业务计划数据，比如版本上线、大促排期、渠道投放计划，这是容量预测区别于普通时序预测的关键。模型输出重点是饱和时间预估，而不是简单的资源数值。同时要做多场景推演：基准流量、峰值流量、叠加故障的复合场景，给出不同水位下的扩容窗口期。预测结果输出后，要配套资源调度策略，区分静态预留、弹性伸缩、离线任务错峰，平衡成本和稳定性，避免一味堆资源。

故障演练是容量方案的验证手段。很多容量方案只在理想流量下测算，一旦叠加依赖故障、网络抖动，容量瓶颈会提前暴露。演练设计上，优先选择和容量相关的场景：流量突增、下游服务延迟升高、缓存失效、数据库连接耗尽。演练前划定流量边界，设置熔断和止损开关，保障业务底线。演练过程中持续观测容量指标，对比预测的饱和拐点和实际发生拐点，找到预测偏差来源。

整套流程的闭环逻辑是：基于业务计划做容量预测→输出扩容和弹性策略→通过故障演练验证峰值 + 故障叠加场景下的真实承载力→根据演练偏差修正资源转化率、调整预测模型参数。落地时要先区分核心业务和非核心业务，核心链路优先建立容量基线，非核心业务以弹性降本为主。同时容量预测要持续迭代，每一次大促、每一次版本变更之后，都要复盘实际消耗和预测值的差距，沉淀修正因子。

容量管理本质是稳定性和成本的权衡，故障演练则是剔除容量方案里的理想化假设。这套技法落地之后，运维不再靠经验拍脑袋评估资源，而是用数据驱动容量规划，用演练验证方案可靠性，实现资源成本可控、业务峰值稳定兜底。
